# 06 — Carrier client (`packages/camara-client`)

> Load `00-conventions.md` first. Depends on: 04 (mock running), spike 02B (Gateway verdict). Day 4. `DirectClient` is built here and is complete; `GatewayClient` gets its shape here and its wiring in prompt 13.

## Goal

The `CarrierClient` protocol Tower and Alerts call, with the error mapping, timeouts, the circuit breaker, the backend switch, and a conformance fixture set that both implementations must pass identically.

## Steps

1. Protocol + result types + config. `make_client(config)` picks the implementation from `config.client` (`direct` | `gateway`), which is orthogonal to `backend` (mock | sandbox).
2. `DirectClient` against the mock, operation by operation; fixtures generated by a small script from the vendored specs (`scripts/gen_fixtures.py`) so they stay in step with the mock.
3. Error map, timeouts, breaker — as middleware around the HTTP call, shared by both clients.
4. `GatewayClient` with the fake Gateway: an in-process FastMCP server exposing tools named per Gateway's convention (from spike B; if unknown, `<api>__<operationId>`), forwarding to `DirectClient`. The point is identical results through both paths.
5. Backend-swap test with two mock containers.

## Acceptance

- Both implementations pass the same fixture suite with byte-identical result objects.
- Error table test enumerates every `code` found in `specs/camara/*.yaml` error schemas — none unmapped.
- Request-profile call never exceeds 350 ms wall time under injected timeout.
- `test_hygiene` green.

## Guardrails

- The E.164 is decrypted by the caller and passed in; this package never touches `msisdn_enc` or KMS. It never logs the device object.
- No retry on the request path. Ever.
- Don't paper over spec differences between operations with a generic "call" helper that hides the path — one method per operation, path from the spec.
